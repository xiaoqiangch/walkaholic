# 探索基金（金币经济）与防作弊

> 状态：已实现（account 服务 + Web 客户端），108 项测试通过

## 一、为什么这样设计

### 问题：供给侧的负期望

最初设计是「埋盒扣押金 10 金币，被找到才返还 + 奖励」。
多账号模拟 7 天后暴露出致命问题：

| 玩法 | 7 天结果 |
|---|---|
| 只找不埋 | 100 → **2010**（+1910） |
| 只埋不找 | 100 → **0**（-100，押金全沉没） |
| 埋 + 找 | 100 → 1660 |

**结论：只埋不找的人会破产。** 而供给侧（埋）才是社区冷启动的关键——没人埋，找的人也没东西找。经济系统如果惩罚供给，整个循环会塌。

### 修复：零成本埋 + 高额供给奖励

| 参数 | 值 | 理由 |
|---|---|---|
| 初始资金 | 100 金币 | 够玩一整周，不被零资产劝退 |
| **埋盒押金** | **0** | 供给侧不能有负期望 |
| **埋主奖励**（被找到） | **45** | 高于单次寻宝上限（40），因为供给更稀缺 |
| 寻宝基础 | 15 | |
| 距离加成 | +0~15（满 2km） | 走得远更有价值 |
| 首寻加成 | +10 | 鼓励探索没人去过的地方 |
| 单次寻宝上限 | 40 | |
| 日收益上限 | 300 | 防刷 |
| 日埋上限 | 5 | 防垃圾点刷屏 |
| 埋点最小间距 | 50m | 防同一地点反复埋 |

## 二、边际递减（两套）

### 寻宝侧（找得越多，单次越少）
| 当天第几次 | 系数 |
|---|---|
| 1–3 | 1.0 |
| 4–6 | 0.7 |
| 7–10 | 0.4 |
| 11+ | 0.2 |

### 埋主侧（被找到越多，单次越少，**更陡**）
| 当天第几次被找到 | 系数 |
|---|---|
| 1 | 1.0（45） |
| 2 | 0.75（34） |
| 3 | 0.5（23） |
| 4 | 0.3（14） |
| 5+ | 0.15（7） |

**为什么埋主侧要更陡**：埋一次可以被多个人找。如果不递减，「1 主号 + N 小号」的农场攻击里，小号去"找"主号埋的惊喜，主号每次稳拿满额 45，作弊收益远超诚实玩家。

**实测数据**（7 天，1 主 + 5 小号）：
- 不减前：农场 **2.56×** 诚实玩家（按总收益）
- 加埋主递减后：按账号算农场 **0.32×** 诚实玩家（作弊亏本）

## 三、防作弊（6 道防线）

| 威胁 | 手段 | 判定 |
|---|---|---|
| **自埋自找** | 服务端强制 | `OWN_SURPRISE` — 不能找自己埋的 |
| **同设备刷** | 设备指纹（IP+UA 哈希） | `SAME_DEVICE` — 不给币 |
| **同 IP 刷** | 注册 IP 交集检测 | `SAME_IP` — 不给币 |
| **两人互刷** | 配对日限 | `PAIR_LIMIT` — 同对用户每天最多结算 2 次 |
| **速度作弊** | 时间门槛 | `TOO_FAST` — 埋下到被找到 < 60 秒不计收益 |
| **批量注册** | 同 IP 注册限 | `REGISTER_IP_LIMIT` — 同 IP 24h 最多 3 个号 |
| **垃圾点位** | 间距 + 日限 | `TOO_CLOSE`（<50m）/ `DAILY_BURY_LIMIT` |
| **收益爆炸** | 日上限 | `DAILY_CAP` — 每天最多 300 |

### 关键公平性设计：被拦下时埋主仍拿回押金

即使找人被判作弊，**埋主不应承担损失**（他可能是无辜的）。
代码：`settleFind` 在 `!check.allowed` 分支里仍给埋主退还押金。

| 场景 | 内容 | 断言 |

| 2 | 2 用户恶意互刷 50 次 | 日收益 ≤ 300 |

## 五、API

| 接口 | 说明 |
|---|---|
| `GET /api/wallet` | 余额 + 今日收益/上限 + 今日埋盒数 + 经济参数 |
| `GET /api/wallet/ledger` | 最近 60 条金币流水 |
| `GET /api/wallet/leaderboard` | 金币榜 Top 20 |
| `POST /api/surprises` | 埋盒（触发余额/日限/间距检查，零成本不扣钱） |
| `POST /api/surprises/:id/find` | 找盒（触发结算，返回 `economy` 明细） |

`POST .../find` 支持 `X-Travel-Meters` header 上报行走距离（距离加成用）。

## 六、流水类型

| kind | 含义 |
|---|---|
| `initial_grant` | 注册启动资金（+100，**不计入日收益**） |
| `bury_reward` | 埋主因被找到获得 |
| `find_reward` | 寻宝者获得 |
| `bury_deposit` | 押金（当前为 0，保留字段） |
| `bury_refund` | 押金退还（当前为 0） |

## 七、已知限制

1. **没有跨天配额累积**：日上限是硬重置，不可积攒。如果想要"周末多玩"，需要加配额累积机制。
2. **`X-Travel-Meters` 由客户端上报**，可被篡改。目前只影响最多 +15 金币的距离加成，且受日上限兜底，风险可接受。若要做严格验证，需要服务端用轨迹计算。
3. **设备指纹依赖 IP+UA**，同一 NAT 下的不同用户可能被误判为同设备。当前只在"找到"时判定，误判后果是不给币（不影响使用）。
4. **金币目前没有消费出口**，只有积累。要形成完整经济循环，后续需要设计消耗场景（如"用金币提高盲盒品质""兑换稀有卡片"）。
